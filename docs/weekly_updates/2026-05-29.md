Playwright loaded *every URL we tried* until 2026-05-19; then walled 9/9 on 2026-05-26 on the Air. The discriminator (regular Chrome loaded the same URL cleanly on the same Mac, same time, while Playwright HITL was failing) **proves the block is the automation fingerprint, not the IP or account**. Cheap convention; expensive omission if missed.

## One new framing + one refinement of last week's

1. **(New) "3 legs to the WI chain — and only one of them is still a scraping problem."** The 6 pairwise relations among {principal, lobbyist, lawmaker, bill} decompose into 3 legs: lobbying data (legs 1-3, all 3 relations from one corpus, materialized this week), legislature bills (leg 4, primary sponsorship from Plural Policy bulk CSV, materialized this week), and campaign finance (legs 5-6, both $-flow relations from CFIS, scoping in Phase 4). **Each state ships one of these legs on its own clock** — WI lobbying data exists today, Plural Policy bulk CSV exists for every state with a legislature, CFIS analogs exist in every state with a campaign-finance disclosure law. The leg-by-leg structure means **partial-state coverage is still useful output** (one-leg-deep-on-many-states ⊕ three-legs-deep-on-few-states); the project doesn't have to pick.

2. **(Refinement of last week's "gather first")** Last week's framing said: "collect per-(state, vintage, question) answers in flexible intermediate JSON, then design v2.2 schema from observed reality." This week's WI work refines that: **the gather-first principle applies to schemas, not to file formats**. The WI lobbying data is **already in a structured tabular shape** (6 TSVs, 4,798 typed rows), and the schema fit (`LobbyingFiling` v1.2) was high (4 gaps in 4,798 rows). What v2.2 still needs to design — and what statutes-into-JSON gather-first is the path to — is the **legal-axis side of the SMR** (what does the statute require?), where typed cells failed on qualitative-trigger states. The portal-data side ("what does the state actually expose?") didn't have that problem; the existing schema fit fine. **v2.2 design only blocks the legal axis, not the practical axis.** Worth surfacing because it means Track B (portal extraction) can keep moving on the existing schema without waiting on v2.2.
