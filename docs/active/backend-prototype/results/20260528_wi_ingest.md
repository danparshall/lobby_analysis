## Schema gaps surfaced (deferred — flag at next sync)

These are **observations**, not blockers. The prototype works without resolving them.

1. **`total_hours_communicating` + `total_hours_other`** — WI tracks per-filing hours for both principal and lobbyist filings (1,706 + 3,092 = 4,798 rows have these). `LobbyingFiling` has no hours field. Currently dropped at ingest. Could be added as `total_hours_communicating: float | None` + `total_hours_other: float | None` in v1.4, or modeled as a generic `metric` map. **Note**: lobbyist hours are the *only* numerical signal on lobbyist filings — WI lobbyist filings have no `total_expenditure` field at all. So dropping hours means lobbyist filings are now mostly empty shells in our schema. Worth fixing before locking v1.

2. **`WI_principal_bill_efforts.tsv`** — 7,345 rows of `(principal_id, bucket, item_id, item_name, item_description, period_label, percent)`. These are positions on bills, but they're **not directly attached to filings**. They're keyed on `(principal, bucket, period_label)`. To attach as `LobbyingPosition[]` on the principal filings, we'd need to fuzzy-match `period_label` ("2025 January - June") → `reporting_period_start/end` (`2025-01-01` → `2025-06-30`). Tractable but a separate slice. Skipped here; the v0 ingest stores positions = `[]` on every WI principal filing.

3. **`WI_lobbyist_principal_authorizations_unified.tsv`** — 2,254 rows describing which lobbyist is authorized to lobby for which principal during which window. There's no obvious home for this in `LobbyingFiling` or `LobbyistRegistration` as currently shaped. Looks like it should map to `LobbyistRegistration` with `(lobbyist, principal, authorized_on, withdrawn_on)`. Skipped here; deferred.

4. **`(agent, employer)` tuple problem** still latent — irrelevant for WI principal filings (the filer is the org, no agent), but for the 3,092 lobbyist filings the lobbyist has no associated "employer" field in `LobbyingFiling`. The authorizations TSV (point 3) is where this should live; same gap as flagged on `oh-portal-extraction`.

## What the prototype now demonstrates

A fellow can run:

```bash
# Ingest (3 sec)
PYTHONPATH=src .venv/bin/python -c "
from pathlib import Path
from lobby_analysis.backend.ingest_wi import ingest_release_dir
from lobby_analysis.backend.storage import init_engine
print(ingest_release_dir(Path('releases/wi'), init_engine('data/backend/prototype.db')))
"

# Serve
BACKEND_DB=data/backend/prototype.db PYTHONPATH=src .venv/bin/python -m uvicorn \
    lobby_analysis.backend.api:app --port 8765

# Query
curl 'http://localhost:8765/search?q=DoorDash'  # 2 hits, $2.18M YTD
curl 'http://localhost:8765/filings?state=WI&filer_role=client&limit=10'
curl http://localhost:8765/filings/WI-principal-10936-expenditure-2025-H1
```

That's the smallest-viable backend for state lobbying data, populated with one real state's filings, queryable over HTTP. Reasonable foundation to layer on what we cut from Gowrav's full spec — first natural addition is FTS / richer search, since `/search` currently only matches filer name (won't find bill numbers, period labels, etc.).
